# 联智中枢（LZCore）目标驱动 Loop Engineering 工程规范

> **Enterprise Goal-Driven Loop Engineering & Autonomous Recovery Specification**
> 本规范系统阐释 LZCore 核心认知循环（QueryLoop）的多轮迭代机制、目标断言状态机、只读自愈流水线以及长程任务可靠性保障。

---

## 1. 认知循环哲学：证据驱动与目标闭环

在复杂企业系统排障与配置变更场景中，大语言模型面对的往往不是“单次提问-单次回答”的简单交互，而是包含海量外部不确定性的**长程因果决策链条**。

传统的 Agent 往往存在两大设计缺陷：
- **静态硬编码轮次**：设定“重试 3 次失败即整体报错”，将网络偶发抖动错误地定性为整个运维任务的失败；
- **盲目重放导致副作用**：在遇到外部写入超时或状态未明时，机械重放带有副作用的写操作，直接引发严重的生产事故。

联智中枢引入了先进的 **目标驱动 Loop Engineering** 范式：
- 系统不以累计物理时钟或死板的循环步数作为任务终止的依据；
- 推进逻辑完全由**结构化目标缺口（Goal Gaps）**与**受验证客观证据（Verified Evidence Claims）**共同驱动。

## 2. QueryLoop 每轮核心因果执行流水线

每轮推理生命周期由底层引擎严密把控，确保每一步操作均满足合规性与确定性：

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 1. 上下文装配与模型推理                                                │
 │    结合用户请求、受治理上下文与已有证据，模型输出受控工具提案或最终答复 │
 └───────────────────────────────────┬────────────────────────────────────┘
                                     │
                                     ▼
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 2. 计划依赖与结构性边界静态校验                                        │
 │    运行时核定 plan_step_id、依赖关系、参数 Schema 与 Skill 授权切片     │
 └───────────────────────────────────┬────────────────────────────────────┘
                                     │
                                     ▼
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 3. 治理网关统一执行 (ToolRuntimeClient.invoke)                         │
 │    执行拦截器 (execution_interceptor)、沙箱执行、敏感数据动态脱敏      │
 └───────────────────────────────────┬────────────────────────────────────┘
                                     │
                                     ▼
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 4. 标准化结果投影与证据索赔提取 (Evidence Claims)                      │
 │    生成结构化 ToolResult，将真实物理事实映射为标准化证据声明            │
 └───────────────────────────────────┬────────────────────────────────────┘
                                     │
                                     ▼
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 5. 目标核销与自愈推进 (Goal Closing & Autonomous Recovery)             │
 │    · 核销已满足的恢复目标                                              │
 │    · 针对可恢复只读异常注册新目标或向模型发送确定性 Nudge 反馈          │
 └───────────────────────────────────┬────────────────────────────────────┘
                                     │
                                     ▼
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 6. 权威断言门禁检查 (Recovery Final Gate)                              │
 │    核对全域目标达成度与覆盖率账本，决定继续推进下一轮迭代还是安全终态   │
 └────────────────────────────────────────────────────────────────────────┘
```

## 3. 异常分类矩阵与处置准则

平台针对生产环境中可能出现的不同类型异常，制定了严格的差异化应对矩阵：

| 异常情景与事件特征 | 运行时处置机制 | 模型侧行为与后续决策 |
| :--- | :--- | :--- |
| **常规只读工具执行异常**<br>*(如接口偶发抖动或网页抓取失败)* | 记录建议性的只读恢复目标；失败本身不具有否决效力。 | 模型根据整体诉求自主选择寻找替代证据链（如换用等价工具）或如实结束任务。 |
| **领域强约束证据缺失**<br>*(扩展显式声明了核心证据指标)* | 启动严格核验机制，实时比对证据类型、事实属性与资源范围。 | 模型必须成功取得对应的物理证据切片，否则系统拒绝放行终态。 |
| **CLI 语法或参数被设备拒绝**<br>*(命令在特定版本固件下不支持)* | 拦截器捕获底层驱动反馈，将其包装为 `model_recovery_guidance` 结构化线索返回。 | 模型读取指导线索，自主决定修正语法、换用语义事实或查阅操作手册，严禁平台无脑重试。 |
| **多目标中的单一设备失联**<br>*(巡检 100 台交换机中 1 台掉线)* | 将故障隔离在故障设备的专属上下文中，其余 99 台设备流水线继续推进。 | 模型在最终成果中清晰呈现各设备覆盖率账本（成功集/失败集/缺失集），不整体报错。 |
| **超出已发布 Skill 授权范围**<br>*(模型试图跨越边界操作未授权节点)* | 鉴权网关果断拒绝并回传标准权限违规错误。 | 模型获悉授权边界，调整后续规划或明确向用户报告权限限制。 |
| **外部写入结果未知 (Unknown Write)**<br>*(下发配置过程中网络链路中断)* | 作为完整物理事实返回，状态标记为 `unknown`；**坚决禁止平台自动盲目重试**。 | 模型根据业务重要性决定发起主动回读（Read-back）、继续配置、或向运维人员报警。 |
| **外部写入明确失败 (Write Rejected)**<br>*(设备返回配置冲突或只读视图限制)* | 记录失败详情并完整交由模型。 | 模型停止当前写入序列，分析失败原因并向用户反馈整改建议。 |
| **开启审批流的高危配置调用**<br>*(Skill 开启 approval_enabled)* | 核心拦截器就地冻结该调用，持久化 QueryLoop 快照并释放物理资源。 | 挂起等待外部人工审批；通过后服务端自动原样回填真实结果并无缝恢复执行循环。 |

## 4. 目标、证据与结构性边界控制

### 4.1 证据索赔严密性（Evidence Claims Validation）
- **关联并非完成**：模型在后续回合中可在工具调用中使用 `plan_goal_ids` 挂载已打开的目标 ID，但这仅作为逻辑关联提示。
- **真实闭环校验**：运行时引擎会对该调用的底层能力类型、关联资源身份（如 `device_id`、`connection_id`）以及返回的证据结构进行严格核验。**只有已成功执行且具备确定性物理终态的只读观察结果，才被允许销毁该目标**。

### 4.2 消除人为墙钟限制（No Cumulative Wall-Clock Limit）
企业级自动化巡检与多维度诊断可能耗时数分钟乃至数十分钟。联智中枢：
- 不设置累计物理运行时间上限；
- 依托异步作业与长任务轮询机制，严格遵从底层工具上报的状态生命周期和人工终止信号；
- 外部依赖项自身的物理连接超时仅作为工具事实记录，绝不被平台粗暴曲解为“系统总时间耗尽”。

### 4.3 会话上下文与 Token 保全
模型输入与输出杜绝在中间层进行粗暴的文本截断。若底层大模型 Provider 触发了长度上限或流式中断，QueryLoop 完好保留已接收的前缀文本并在相同上下文下向模型发送继续指令，直至拼接完成完整的逻辑闭环。

## 5. 子 Agent（Subagent）递归委派契约

在面对大规模分析任务时，主 Agent 可通过 `agent.manage` 启动子 Agent 协同工作：
- **同等工具面继承**：子 Agent 在运行时层面与父 Agent 共享同一套 Canonical 工具治理总线；
- **分工契约而非权限阉割**：Subagent Profile 仅用于限定任务分工、特定角色 Prompt 与输出交付规范，绝非低权限旁路。父任务若关联了特定网络 Skill，服务端为子 Agent 重新核定该 Skill 范围并下发对应的设备切片；
- **独立生命周期**：子 Agent 不受人为墙钟硬限制，支持运维人员在前端工作台随时发起定向中断。

## 6. 状态正交与外部操作账本（Ledger）

```text
 ┌────────────────────────────────────────────────────────┐
 │   用户任务终态: execution_outcome                      │
 │   [ complete | partial | blocked | failed | unknown ]  │
 ├────────────────────────────────────────────────────────┤
 │   单次工具尝试: tool_execution_outcome                 │
 │   [ success | error | timeout | rejected | unknown ]   │
 └────────────────────────────────────────────────────────┘
```

1. **客观记录工具事实**：`tool_execution_outcome` 真实记录每次底层尝试。若在发生某次工具失败后，系统通过备用渠道取得了满足诉求的只读证据，用户的 `execution_outcome` 依然可以判定为高置信度的 `complete`。
2. **外部写入收敛机制**：若后台进程遭遇突发断电或重启，对于原本处于 `unknown` 状态且失去追踪信标的陈旧任务，账本将其客观收敛为 `indeterminate` 终态——真实留存“该操作因外部原因最终无法确认结果”的审计记录，坚决拒绝将其粉饰为正在运行中或假装成功。
