## 实际调用链与修复

AgentSession → QueryLoop → ToolRuntime → ToolRuntimeClient → schema/caller/policy → 领域文件实现 → 结果脱敏及审计。确定性测试也通过 RuntimeClient，不用直接 handler 成功替代实际调用。

| 确证问题 | 修复 |
| --- | --- |
| CSV 发布变成 `.csv.txt`，文本分支归一化换行；空文件/UTF-16 发布失败 | publish 统一注册原始字节及扩展名，再封存 Artifact 元数据和引用，保留既有文本密钥发布约束。文本报告生成仍是独立动作。原始投影不再虚报 redaction_applied。 |
| 文本提取、检查、正文索引及 FileStore 读取以替换字符吞掉解码错误；源码编辑仅支持 UTF-8 | 共享严格文本解码，自动识别 Unicode BOM；显式 encoding 支持已知旧编码。读取与编辑按同一合同，保留原编码/BOM/换行；无法编码的改动不写入。默认不猜 GB18030 等编码。 |
| 旧全文索引会继续复用同一 hash 下曾错误解码的内容 | disposable SQLite 索引通过 user_version 一次性作废旧投影；原件和 FileRecord 不变。解码失败不入索引，搜索返回 failures。 |
| 损坏 ZIP 后部 CRC 失败，前面成员已出现在目标目录，结果未带明确文件错误 | 同级临时目录完整解包后发布；CRC/TAR 错误明确失败，目标目录和临时半成品不保留。路径/链接/名称/大小校验继续执行。 |
| 模型将文件库列表当作源码目录，或给逻辑文件夹加物理存储前缀 | list 返回 managed_files，物理列表返回 source_directory；schema 明确注册文件范围、逻辑 folder 与 source_move 的物理移动区别。没有按关键词过滤工具、重映射路径或新增持久状态。 |

## 三轮确定性验证

- 1,299 次最终 RuntimeClient 调用，三轮各 433 次，无失败。32 类扩展名：TXT/MD/CSV/TSV/JSON/YAML/XML/HTML/CFG/LOG/PY/JS/TS/RS/SVG/PNG/JPG/BMP/PDF/DOCX/XLSX/PPTX/DOC/XLS/PPT/ZIP/7Z/MP3/WAV/MP4/CUSTOM/BIN。此部分使用不透明原始 payload，证明管理能力与扩展名无关，不声称这些 payload 是可解析的真实文档。
- 原件导入、准确身份/摘要、跨工作区拒绝、显示名与逻辑目录、独占工作副本、物理重命名/移动、回收/恢复、目录移动和 ZIP 字节往返。文本另测 UTF-8（带/不带 BOM）、UTF-16 LE/BE、UTF-32 BE、GB18030、CP1252 的读取、dry_run、精确编辑、patch、发布及提取，独立核对完整原始字节。
- 84 次实际格式 RuntimeClient 调用，三轮各 28 次。执行器生成真实 DOCX/XLSX/PPTX/PNG/BMP/PDF；结构读取、提取、图片证据与 PDF 页图真实存在。修改 DOCX 正文、XLSX 单元格（保留公式）、PPTX 标题、PNG 像素后重新发布；独立处理器验证内容，旧原件逐字节不变。这一组仅在临时进程开启已实现的可信本机 Python 模式，不修改产品配置，不冒充强隔离容器或 Windows 原生验证。最初脚本误把 Python 临时 cwd 当工作区，3 次尝试生成到了临时执行目录；改用明确 input_data 工作区后通过，没有为测试扩大生产权限。
- 9 次故障流程调用，三轮注入 Artifact 元数据提交故障。实际载荷已写入时返回 EXECUTION_UNKNOWN、原 file_id/Artifact 身份与禁止自动重放；preview/apply 只核对并封存元数据，payload_writes 均为 0，原写入只尝试一次。
- 损坏 ZIP 单独故障注入在旧实现留下 first.txt/last.bin；修复后返回 archive_integrity_check_failed，executed=false，无目标目录及临时半成品。

## 真实模型及边界

MiniMax-M3，完整生产工具目录和 AgentSession，三个独立工作区，各做源码管理、未知原件管理、原始文件发布三任务。试验只在调用方设置请求/耗时停止条件，不限制生产 loop。

首轮共 77 次 Provider 请求，9 个任务，独立目标核对 4 个通过，5 个未通过；不能把 errors=[] 或模型声称完成当通过。其中一组把逻辑目录填成物理前缀；一组自行拼 UTF-16 字节，把“新”写成 U+0B65 且错误声称核对通过；一组从托管列表错误推断未登记源码不存在。两个后续发布目标因前置源码未完成而未通过，发布本身对实际输入的字节保持正确。

收尾复测 41 次 Provider 请求：逻辑目录纠正、第三工作区的完整源码管理和发布通过独立核对；错字一组已通过 workspace.file 精确编辑完成副本及原路径纠正，但模型绕到副本发布/导入和引用处理，24 次请求后被测试上限取消，未将这一完整任务计作通过。其后准确源路径的最终发布补验 7 次请求通过。最终再次独立核对三个工作区各 8 个目标：源码完整字节、实际改名、旧文件删除、说明创建、原件身份/逻辑目录/恢复后的字节、工作副本，以及两种原件的最新发布，24 个目标均成立。合计 125 次真实请求包含失败定位、取消及纠正，不能称为 125 次全部任务一次成功。不重放未知写入，没有删除引用中的旧证据，也没有为测试放开执行权限。

任意类型原件在当前 200 MiB 文件存储限额内可导入、复制、组织、发布、回收与恢复。语义读取、修改、渲染依赖格式处理器和实际权限：没有安装旧 Office、7z、音视频处理器时如实保留原件和说明边界，不能承诺理解所有二进制格式。上述样本证明相应操作链，不保证所有模型一次规划正确。
