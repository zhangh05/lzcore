# Agent 任务评测

用真实模型、真实服务跑一组固定任务，看 agent 能不能把事情办成。`harness/` 里的测试管的是"代码对不对"，这里管的是"agent 好不好用"。

## 怎么跑

先用 `./start.sh` 启动服务，然后在仓库根目录执行：

```bash
.venv/bin/python3 evals/run.py --provider minimax
```

本机日常评测用自定义的 test（gpt-6.1-sol）服务，MiniMax 额度有限。

- `--provider`：模型服务 id，和对话输入框里能选的一致（如 `minimax`、`custom`、`ollama`）。
- `--only a,b` / `--category 数据,文件`：只跑部分任务。
- `--tag hard`：只跑困难任务（带 `hard` 标签的 15 个）。
- `--skip-network`：跳过需要外网的任务。
- `--keep`：保留每个任务的临时工作区，方便排查。

每个任务在独立的临时工作区（`ev<时间>-<任务id>`）里运行，`fixtures/` 会先放进工作区的 `files/data/`，结束后工作区自动删除。结果写到 `evals/results/<时间>-<provider>/`：

- `results.jsonl`：每个任务一行，包含每轮回复、工具调用链、运行时修复事件、token 用量。
- `report.md`：通过率、分类成绩、工具使用与失败率、运行时修复介入次数、失败详情。

脚本不读取任何密钥，模型和密钥由服务端按 provider 解析。真实调用会消耗模型额度：一轮完整评测（51 个任务）大约 200 次模型调用。

## 加任务

在 `tasks.yaml` 里追加。判定只用确定性规则：回复正则、回复长度上限（`answer_max_chars`）、输出文件内容、是否调用了工具，以及在工作区里跑一条验证命令（`exec`，例如跑测试看退出码和输出）。期望值要能从 fixtures 算出来，计算过程用代码验证过再写进去。`harness/evals/test_eval_suite.py` 会在 CI 里检查任务定义是否合法，不会调用模型。

## 困难任务

基础任务现在已能全部通过，区分度不够，所以加了一组 `hard` 任务：脏数据清洗、多表关联、日志统计、批量改配置、修 bug 并让测试通过、单位换算、复利计算、多步长链路、结构化抽取成 JSON、相对日期和不存在的数据（考诚实）、多轮改需求、多条记忆组合使用、打包解压、字数限制。报告里会单独列出基础和困难两档的通过率。

## 用法建议

- 改 prompt、工具定义、运行时逻辑之前先跑一次基线，改完再跑一次对比。
- 同一模型多跑几次再下结论：模型输出有随机性，单次相差一两个任务不说明问题。
- `report.md` 里的「运行时修复介入」统计运行时替模型兜底的次数。这个数如果很高，往往说明工具接口和模型之间对不齐。
